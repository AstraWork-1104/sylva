# Flora - актуальные инструкции репозитория

## Действующий дизайн

Ветка `flora-ui-v2`, папка `flora-ui/` - утверждённый визуальный референс. Сверяйте исходники `index.html`, `styles.css`, `app.js`; `Flora-UI.html` - автономная упаковка того же прототипа. Не использовать другие ветки и старые README как источник новых требований. GitHub доступ и официальные технические справочники разрешены по необходимости.

HTML/JS - визуальная демонстрация, а НЕ работающий плагин Autodesk 3ds Max. Настоящая Flora реализована на Python/PySide6/MAXScript, реальные данные - из индексированной .max-библиотеки и SQLite FloraAtlas v1. При переносе в PySide6 сохранять функционирующие Explorer, Favorites, Basket, Catalogs/FloraCOL, Drag & Drop, Corona Proxy/Merge, материалы и пользовательские настройки.

## Точные границы будущего таска PySide6 (20.10.2026)

Согласованы четыре **локальные** правки после отдельно выданного Point Cloud + Properties: новая Scene с группировкой FloraSource, навигация Explorer слева / Catalogs → Scene → Favorites → Basket справа **с иконками и видимыми подписями**, **зелёная точка** Scene Presence и визуальная группировка существующего Settings по макету. Новый таск Codex на четыре пункта ещё не выдан. **Никакого глобального редизайна или рефакторинга рабочего плагина:** остальные Explorer, Filters, Basket, Geometry/Corona Proxy Import, Proxy Cache, материалы, сцены и пользовательские данные не трогать. Подробнее - [раздел 19 основного описания Flora](https://docs.google.com/document/d/19MQLTbmyikvPj2wCLwIvuSqF3sdwJ8YUlSEtsMSkbZ0/edit).

## Визуальный стиль

Сохранять спокойный тёмно-зелёный плоский дизайн без глянца, рельефа и выпуклых кнопок. Сохранять адаптивность, корректное выделение и прокрутку. Не генерировать изображения вместо редактирования реальных UI-файлов. При изменении CSS/JS синхронизировать `Flora-UI.html`, проверить JavaScript и отсутствие устаревших декоративных стилей.

## Актуальная классификация и Filters

Реализованное в браузерном дизайне поведение Filters: `Группа растения` (Все группы, Деревья, Кусты, Трава) -> зависимая `Категория растения` (недоступна до выбора группы); `Тип среды` (Все среды, Природные, Домашние) -> зависимая `Категория среды` (недоступна до выбора типа); `Цветение` (Все, Да, Нет); `Высота, см` (неактивные От/До до точного анализа). Категории групп: Деревья - Лиственные, Хвойные, Пальмы; Кусты - Лиственные, Хвойные, Папоротники, Злаки, Вьющиеся, Многолетники, Суккуленты; Трава - Травы, Цветы, Почвопокровные, Луковичные. Природные среды: Лесная, Луговая, Водная, Прибрежная, Степная, Пустынная, Горная; Домашние: Улицы, Парки, Сады, Дворы, Интерьеры. Родительский выбор сбрасывает дочерний. Компоновка автоматически 4/2/1 колонка по ширине центральной панели с собственной вертикальной прокруткой при уменьшении высоты.

В SQLite `natural_json` и `landscaped_json` остаются массивами нескольких значений; «Домашние» - имя UI для `landscaped_json`. `similar_json` - массив связанных `plant_id` растений из того же Atlas. Ботанический FloraCat больше не использовать, тематический FloraCOL сохранять.

## Дополнительно согласованные изменения для рабочего плагина

Без отдельной внутренней шапки Properties и без настройки видимости/порядка полей: раскрываемые «Названия» и «Ботанические сведения», фиксированный набор полей. Grid: модель, под ней русское и английское названия при наличии, без Vol. Table: только актуальные RU/EN/Latin, цветение, группа/категория, тип/категория среды. Поиск: filename, RU/EN/Latin и названия связанных похожих растений. Settings: очистка импортированных метаданных/каталогов с подтверждением и сохранением Favorites, коллекций, библиотеки, сцены и исходных файлов.

**Различать статусы:** многие из этих элементов уже представлены в веб-макете; это не доказывает их реализацию в 3ds Max. Для HTML сверять UI_MAP.md/фактический код, для рабочего плагина - его текущие исходники и host-проверки. Не возвращать Scatter или пакетную автоматическую генерацию превью.

## Ответственность и передача результатов

Пользователь утверждает продуктовые решения. Отдельный чат-архитектор помогает с требованиями и по запросу формулирует задания Codex, но не берёт на себя код, математические алгоритмы и сборку. Codex исследует рабочие локальные исходники, сам выбирает технический способ реализации, проверяет и сохраняет результат в привычную ЛОКАЛЬНУЮ папку пользователя. Административный чат поддерживает Google-документы; его одобрение каждого задания не требуется. Файлы, создаваемые самим ChatGPT, пользователь предпочитает получать с Google Диска. Не вводить по умолчанию обязательные Issues/PR, CI/CD или загрузку сборок в облако.

Инструкция для чата-архитектора: https://docs.google.com/document/d/1Ohlf7RkIipPuNebNaDxLjsZ6TSHqbooHe0jdwukpR6g/edit

## Чат сопровождения UI V2

Непосредственное обновление браузерного макета выполняет отдельный **чат UI-дизайна**, руководствуясь подтверждёнными решениями пользователя и актуальным описанием Flora. Инструкция роли: https://docs.google.com/document/d/1POnwC_A4-ia7DAMOzJTLoR7d-4HgBFgalsYxEYZbSaw/edit

Его зона - `flora-ui/index.html`, `styles.css`, `app.js`, синхронизация автономного `Flora-UI.html` и профильных `README.md`, `docs/DESIGN.md`, `docs/SCREENS.md`. Статус правок в документах фиксировать по фактической реализации. Он не меняет Python/PySide6/MAXScript, SQL-контракты и основную Google-документацию; чат-архитектор формулирует продуктовые решения с пользователем, Codex занимается настоящим плагином, администратор - общими документами. Дизайнер не видит автоматически историю другого чата - необходимо передавать подтверждённый итог или сверять актуальное описание.

## Экономия контекста при задачах Codex

Задача Codex должна включать все согласованные требования, точные подписи и состояния UI (включая неактивные селекторы, поиск, счётчики, карточки и множественные значения), границы очистки/сохранения пользовательских данных и проверяемые критерии. Архитектор ИНИЦИАТИВНО проверяет полноту и риски, предлагает оптимальную организацию: одну комплексную задачу, логические этапы в одном запуске либо отдельные задачи по реальным зависимостям и безопасности. Не устанавливать универсальное число этапов, лимит ссылок, длину задания, объём технического поиска или тестов. Цель - минимальный СОВОКУПНЫЙ расход на корректное исполнение без регрессий и переделок, а не самый короткий текст. Filters/Properties/Grid/Table/Search могут рационально разделять один анализ FloraAtlas; опасная очистка импортированных данных может требовать отдельного контрольного этапа. Это примеры, не обязательное дробление. Не требовать автоматически читать все ссылки подряд: открывать нужные части UI V2; профильную SQLite-спецификацию - адресно для совместимости; FLORA_CODEMAP.md использовать как необязательный навигатор со сверкой текущего локального кода. Codex свободен выбирать кодовую архитектуру и технические решения, а также пользоваться интернетом, GitHub и целевыми тестами. Архитектор проверяет текст задания до передачи, но не навязывает пользователю отдельный отчёт о самопроверке.

## Банк будущих идей не является ТЗ

В Flora есть отдельный [чат для обсуждения идей](https://docs.google.com/document/d/1Mng_1SV5dMVfvmmIGSxgQuhuygOTvBhoYErMXMdKNyw/edit) и единый [банк будущих идей на Google Диске](https://docs.google.com/document/d/1UTZxVykKj0NNn96CyqdUP4J150iBLgFWgkrjnbFbbTg/edit). Записи туда добавляются только по явной просьбе пользователя. Они могут быть не утверждены, не исследованы и не включены в план разработки. Не переносить идеи из банка в браузерный макет, рабочий код или текущие инструкции автоматически. После согласования пользователем выбранной идеи архитектор прорабатывает требования; дизайнер обновляет UI только по утверждённому решению. Не нужно читать весь банк перед обычными правками.
